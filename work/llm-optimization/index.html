Using LLMs for Optimization

Can large language models solve hard business optimization problems, such as planning delivery routes, reliably and cheaply? I led the experiments that answered it, and the answer was a design pattern: let the model plan, let a proven optimizer solve, and check everything.

The problem

Asking an LLM to write a whole optimization program is expensive and brittle: long outputs, partial answers, and results that look valid but are not. A business can only rely on an LLM here if it knows which way of using the model gives correct answers at a sensible cost.

What I led

  • A fair benchmark across prompts and providersI designed the experiments and built the benchmark: five prompting strategies on two model providers, run on the same problems and checked the same way. On the main suite, DeepSeek produced valid solutions every time and MiniMax 83% of the time.
  • An outside test to rule out overfittingA standard external benchmark checked that the results held beyond the project's own test cases: valid solutions in every trial, on average 0.07% from optimal.
  • Let the AI plan, let the optimizer solveHaving the model write a short plan for a standard optimizer, instead of the whole program, used 29% of the tokens and cut AI cost 83%, at the same solution quality.
  • Debug the “AI failure” that wasn'tOne apparent model failure was a valid, time-limited solution mislabelled as infeasible. The fix was in how results are read, not in the model.
  • Match the examples to the problemChoosing worked examples that fit the problem variant turned a frequent failure into a stable success.

The result

An LLM works best as a planner inside a checked workflow.

The project catalogued nine ways LLM-generated optimization fails and turned them into practical design rules. The same pattern now shapes how I build every AI system: the model does the judgement-heavy work, proven tools do the exact work, and nothing is trusted until it is checked.
